# 文書の書き方と更新の手順

機能を足す・変えるときに、どの文書をどう直すかの決まりです。人も Claude も、この手順に従います。

## 基本の考え方

1. **読む人ごとに 1 か所。** 同じことを 2 か所に詳しく書かない。利用者・管理者・開発者で書く中身が違うときは、それぞれに書いて互いにリンクする
2. **入口から 2 クリック。** `docs/README.md` → 各ガイドの `README.md` → ページ。新しいページは必ず各ガイドの `README.md` の表に載せる
3. **コードと同じ PR で直す。** 文書だけ後から、はしない
4. **機械で確かめられることは確かめる。** `tests/test_docs.py` がリンク・設定・コマンド・地図への載せ忘れを確かめる

## 文書は画面のヘルプにもなる

`docs/` の Markdown は、docseed の画面の **「ヘルプ」**（`/help`）でもそのまま読めます（[画面](../design/ui.md) S12）。GitHub と画面の両方で読めるように、次を守ります。

- リンクは **相対パス** で書く（`../admin/https.md#…`）。画面では `/help/admin/https#…` に書き換わる
- `docs/` の外（ルートの `README.md`・ソース）へのリンクは、画面ではただの文字になる。読む人に必要な説明は `docs/` の中に書く
- **生の HTML は書かない**（画面では `<…>` がそのまま文字で出る）。使えるのは CommonMark・表・取り消し線・チェックリスト（`- [ ]`）
- 画像は使わない（今は画面に出せない）
- `tests/test_help.py` が、すべての文書が画面に出て、中のリンクが画面の中の見出しまで届くことを確かめる

## GitHub の Wiki（読むための写し）

main に push されると、`.github/workflows/wiki.yml` が `docs/` を GitHub の Wiki に写します（一方向。変換は `scripts/wiki_sync.py`）。

- **編集の元は常に `docs/`。** Wiki で直した内容・Wiki だけに作ったページは、次の同期で消えます
- ページ名は `docs/` のパスから作ります: `docs/README.md` → `Home`、`docs/user/README.md` → `user`、`docs/user/files.md` → `user-files`。名前がぶつかるファイル名（例 `user/files.md` と `user-files.md`）は作らない（同期が止まる）
- 相対リンクは Wiki のページ名に、`docs/` の外へのリンクはリポジトリのファイルの URL に書き換わります
- サイドバー（`_Sidebar.md`）は、各ガイドの目次に出てくる順にページを並べます。新しいページは目次に載せる（[何をどこに書くか](#何をどこに書くか)）
- `tests/test_wiki_sync.py` が、変換した Wiki の中のリンクがすべて届くことを確かめます

初回だけ必要なこと（リポジトリの管理者）:

1. リポジトリの Settings → General → Features で **Wikis** を有効にする
2. Wiki の画面で最初の 1 ページを作る（中身は何でもよい。Wiki のリポジトリは最初のページを作るまで存在しない。次の同期で置き換わる）
3. Actions の画面で「Wiki」のワークフローを手で実行する（Run workflow）か、`docs/` を変えて main に push する

Wiki を誰でも編集できる設定のままだと、同期までの間に書き換えられることがあります。Settings → General → Features の Wikis にある、編集をリポジトリに書き込める人だけに絞る設定（個人のリポジトリでは「Restrict editing to collaborators only」）をオンにしてください。

## 何をどこに書くか

| 変えたもの | 直す文書 |
|---|---|
| 画面に見えるもの（ボタン・画面・操作） | `docs/user/` の該当ページ。新しい機能なら新しいページか節（[利用者向けのひな形](templates/user-feature.md)） |
| 管理者がすること（有効にする・設定する・コマンドを打つ） | `docs/admin/` の該当ページ。任意の機能なら新しいページ（[管理者向けのひな形](templates/admin-feature.md)）と、`docs/admin/README.md` の「任意の機能」の表 |
| `DOCSEED_*` の設定を足した・既定を変えた | `src/docseed/config.py`・`.env.example`・[設定の一覧](../admin/configuration.md)（**テストで確かめる**） |
| `docseed` のコマンドを足した | [コマンドの一覧](../admin/cli.md)（**テストで確かめる**） |
| 更新のときに追加の作業が要る（再処理・マイグレーション以外の手順） | [更新](../admin/upgrade.md) の「版ごとの追加の作業」の表の **一番上** に行を足す |
| 新しい困りごと・エラーのメッセージ | 利用者なら [利用者の困ったとき](../user/faq.md)、管理者なら [管理者の困ったとき](../admin/troubleshooting.md) |
| 仕組み・データ・API・安全策 | `docs/design/` の該当の章（章の番号は変えない。足すときは末尾に） |
| 段階（Phase）が終わった | ルートの `README.md` の段階の表 |
| 調べた・測った | `docs/research/` に新しいファイル（後から書き換えない） |

迷ったら: 「**画面の言葉だけで説明できるか**」。できるなら利用者ガイド、`.env` やコマンドが要るなら管理者ガイド、コードの話なら開発者ガイドか設計書。

## 書き方

### 共通

- です・ます調。短い文。やさしい言葉（画面の文言と同じ言葉づかい）
- 手順は番号付きの箇条書き。条件や一覧は表
- 画面の文言は「」で囲み、**画面にあるとおり** に書く（テンプレートからコピーする）。大事なボタンは **太字**
- 設定・パス・コマンドは `コード` で書く
- 例の名前は `example.com`・`docseed.example.com`・`192.168.1.20`・`<名前>` を使う。実在の人・家の情報は書かない

### 利用者ガイド（`docs/user/`）

- **`.env`・コマンド・コンテナの話を書かない。** 管理者の作業が要る機能は、節の先頭に「**管理者が有効にしたときだけ** 使えます。」と書く（利用者ガイドの README がこの言い回しで案内している）
- 「何ができるか」→「どう操作するか」→「気を付けること」の順
- スマホで操作が違うときは、その場で一言添える（「スマホは右下の **＋**」）

### 管理者ガイド（`docs/admin/`）

- コマンドは **1 つのコードブロックに 1 つ**（そのままコピーして実行できるように）。`.env` の例は `# .env` で始める
- 有効にする手順 → 確かめ方 → 注意 → 関連（設定の一覧の節・設計書の章）の順
- 外部と通信するか・メモリをどれだけ使うかを必ず書く（`docs/admin/README.md` の「任意の機能」の表にも）
- 安全に関わる注意は **太字** で、手順の近くに書く

### リンク

- 相対パスで書く（`../design/api.md`）。リポジトリの外の URL は公式の文書だけ
- 見出しへのリンクは GitHub の形（小文字、記号を除き、空白を `-`）。例: `## パスの下で動かす` → `#パスの下で動かす`、`## HTTPS と入口` → `#https-と入口`、`## 音声・動画` → `#音声動画`
- 見出しを変えたら、`pytest tests/test_docs.py` でリンク切れを確かめる

## 新しい機能のチェックリスト

PR の説明にも同じものがあります（`.github/pull_request_template.md`）。

- [ ] 利用者に見える変更 → `docs/user/` を直した（または「見える変更なし」）
- [ ] 管理者の作業がある → `docs/admin/` を直し、任意の機能なら `docs/admin/README.md` の表に足した
- [ ] 設定を足した → `config.py`・`.env.example`・`docs/admin/configuration.md`
- [ ] コマンドを足した → `docs/admin/cli.md`
- [ ] 更新に追加の作業がある → `docs/admin/upgrade.md`
- [ ] 仕組みを変えた → `docs/design/` の該当の章
- [ ] 新しいページを足した → 各ガイドの `README.md` の表に載せた
- [ ] `pytest tests/test_docs.py` が通る

## テストが確かめること（`tests/test_docs.py`）

| 検査 | 落ちたとき |
|---|---|
| Markdown の相対リンクと見出しへのリンクが切れていない | リンク先のファイル名・見出しを直す |
| コード・compose・スクリプトにある `DOCSEED_*` が、すべて [設定の一覧](../admin/configuration.md) にある | 設定の一覧に行を足す |
| `.env.example` の `DOCSEED_*` が、すべて設定の一覧にある | 同上 |
| `cli.py` のコマンドが、すべて [コマンドの一覧](../admin/cli.md) にある | コマンドの一覧に行を足す |
| `docs/user/`・`docs/admin/` のページが、そのガイドの `README.md` から張られている | ガイドの `README.md` の表に足す |
| （`tests/test_help.py`）すべての文書が画面のヘルプに出て、中のリンクが届く | 相対リンクの先・見出しを直す |
| （`tests/test_wiki_sync.py`）Wiki に写したときに、中のリンクがすべて届く | 同上。ページ名がぶつかるなら、ファイル名を変える |
| 利用者ガイドに `.env`・`docker compose`・`DOCSEED_` が出てこない | 管理者ガイドに移して、リンクにする |
