## 1. 目的とスコープ

Raspberry Pi 5（SSD 起動）1台で動く、自宅/小規模向けのドキュメントサーバーを構築する。

### 1.1 提供する機能

1. **ファイルの保存と共有**: アップロード、フォルダ管理、ダウンロード、ユーザー間のフォルダ共有、外部向けの共有リンク
2. **OCR**: 画像やスキャン PDF から文字を抽出し、検索できるようにする
3. **ベクトル化と検索**: 文書をチャンクに分けて埋め込み、意味検索とキーワード検索を組み合わせたハイブリッド検索を行う
4. **拡張機能（Phase 6〜9）**: 証明書の自動取得、パスキーなどの安全なログイン、URL の取り込み（Web クリップ）、フォルダ・タグの候補と要約（[拡張機能](design/extensions.md)）

### 1.2 スコープ外（初版）

- ~~LLM による回答生成（RAG の生成部分）~~ → 実装済み（任意。小型の LLM を有効にしたとき。[検索設計](design/search.md) 10 章）
- 複数ノード構成、高可用性
- 手書き文字の高精度認識、表・段組みの構造認識
- デスクトップ同期クライアント（版の履歴は実装済み）
- 外部クラウドへの依存（すべてローカルで処理する）。例外として、利用者が有効にしたときだけ、URL の取り込み（fetcher）と OIDC でのログイン（api）が外部と通信する

### 1.3 決定済み事項

| 項目 | 決定 | 理由 |
|---|---|---|
| OCR | **PP-OCRv6 small（検出+認識, 7.7M パラメータ）を RapidOCR + ONNX Runtime で実行** | 2026-06 公開の PP-OCRv5 の後継。日本語を含む 50 言語を 1 モデルで扱う。Pi 5 実機で PP-OCRv5 mobile より速く（3.1 秒 / 3.9 秒）、撮影画像・縦書きで大幅に正確だった。Apache-2.0。tiny は日本語非対応のため対象外 |
| Embedding | **cl-nagoya/ruri-v3-70m（384次元, 最大 8192 トークン）** | 日本語性能が高く軽量。Apache-2.0 |
| Embedding の実行方式 | **ONNX Runtime（fp32）、worker 3 スレッド / api 1 スレッド** | Pi 5 実機で PyTorch と同じ結果のまま、検索クエリの埋め込みが約 5 倍速い（107ms → 22ms）。int8 量子化は 500 文字のチャンクで速くならず、劣化も大きい（cos 最小 0.85）ため不採用 |

| 項目 | 前提 |

                    │   ├─ ファイル管理・共有リンク                          │
                    │   ├─ 検索 API（クエリ埋め込み + ハイブリッド検索）       │
                    │   └─ Web UI                                        │
                    │     │ ジョブ登録            ▲ 結果参照                │

                    │     ▲                                              │
                    │     │ ジョブ取得・結果書き込み                          │
                    │  docseed-worker（外部ネットワークなし）                 │
                    │   ├─ テキスト抽出 (pypdfium2 等)                      │

                    │  SSD: /srv/docseed/{files,db,models,backup,...}     │

### 3.1 コンポーネント

| コンポーネント | 技術 | 役割 |
|---|---|---|
| reverse-proxy | Caddy | HTTPS 終端、アップロードサイズ制限 |
| api | Python 3.12 / FastAPI / Uvicorn（1 プロセス） | REST API、Web UI（Jinja2 + htmx）、認証、検索 |
| worker | Python 3.12（api と同じコードベース・同じイメージ） | テキスト抽出・OCR・埋め込みを非同期で処理 |
| db | SQLite（WAL モード）+ FTS5 + sqlite-vec | メタデータ、ジョブ、全文検索、ベクトル検索を 1 ファイルに集約 |
| storage | SSD 上のローカルファイルシステム | 原本ファイル（内容アドレス）、サムネイル |
| samba（任意） | Samba | LAN からの投入用フォルダ（inbox） |

### 3.2 主な技術選定の理由

- **SQLite + sqlite-vec + FTS5**: 単一ノード・少人数用途では PostgreSQL や Qdrant を別に動かすより軽く、バックアップも容易。Phase 0 の実測で、10 万チャンク × 384 次元の総当たり検索は p95 80ms（float32）。100 万チャンクでは 1 秒近くになる見込み。規模が超えたら Qdrant 等へ移行できるよう、ベクトル検索はリポジトリ層で抽象化する。
- **FTS5 trigram トークナイザ**: 形態素解析器なしで日本語の部分一致検索ができる。2文字以下の語の扱いは [検索設計](design/search.md) 4.3 を参照。
- **ファイル実体（blob）と文書の分離**: 同じ内容のファイルは保存・OCR・埋め込みを 1 回で済ませる（SHA-256 で判定）。
- **独自 API でファイル共有を実装**: Nextcloud は Pi 5 には重く、OCR / 検索との統合も難しい。必要な機能（保存・フォルダ・フォルダ共有・共有リンク）に絞って実装する。
- **Web UI は Jinja2 + htmx**: ビルド工程が不要で軽く、API と同じ Python コードで完結する。
- **ジョブキューは SQLite のテーブル**: Redis などの追加プロセスを持たない。
- **pypdfium2（Apache-2.0/BSD）**: PDF のテキスト抽出とページ画像化に使う。PyMuPDF は AGPL のため採用しない。

## 4. 処理フロー（概要）

詳細は [取り込みパイプライン](design/pipeline.md) と [検索](design/search.md)。

### 4.1 取り込み

```
アップロード / inbox
  → SHA-256 計算・重複判定 → 原本を保存 → process_blob ジョブ
  → [worker] ページごとに抽出（テキスト層 / OCR が必要なページだけ PP-OCRv6）
  → 正規化（NFKC など）→ チャンク分割（目安 600 文字、重なり 100 文字、ページをまたがない）
  → ruri-v3-70m で埋め込み（「検索文書: 」+ ファイル名 + 本文）
  → ready
```

- ページ単位でコミットし、途中で止まっても続きから再開できる。
- 失敗は最大 3 回リトライ。警告（一部ページの OCR タイムアウト等）は ready のまま表示する。

### 4.2 検索

```
クエリ → (A) 意味検索: 「検索クエリ: 」+ クエリ → sqlite-vec で上位 200
       → (B) キーワード検索: FTS5 trigram で上位 200
       → アクセス権・ゴミ箱・絞り込みでフィルタ
       → RRF (k=60) で統合 → 文書単位にまとめる → スニペット・ハイライト
```

詳細は [データモデル](design/data-model.md)。

| 分類 | テーブル |

| 処理 | `jobs` |
| その他 | `settings`, `audit_log`, `schema_migrations` |

## 6. 権限と共有（概要）

詳細は [認証・権限・共有](design/security.md)。

- システムのロールは `admin` / `user`。admin はユーザー管理とシステム運用を行うが、他人のファイルは見られない。
- ファイルの権限はフォルダ単位で、`owner` / `editor` / `viewer`。サブフォルダに継承される。
- 外部の人には共有リンク（閲覧 / アップロードのみ、期限・パスワード・回数制限・無効化）で渡す。

## 7. API と画面（概要）

- API: `/api/v1` 配下の REST API。エラーは RFC 9457 形式。詳細は [API](design/api.md)。
- 画面: ファイル一覧、文書詳細（プレビュー・抽出テキスト・OCR 結果の確認）、検索、共有、ゴミ箱、設定、管理、共有リンクの公開ページ。詳細は [画面](design/ui.md)。

## 8. 非機能要件

### 8.1 性能目標（実機の PoC で確認・調整する）

| 項目 | 目標 |
|---|---|
| 検索の応答時間 | p95 1 秒以内（チャンク 10万件時） |
| テキスト層つき PDF | 1ページあたり 1 秒以内（抽出から埋め込みまで。Phase 0 の実測で 0.5 秒から改定） |
| OCR | 一般的な A4 で 15 秒以内、文字の詰まった写真で 30 秒以内（Phase 0 の実測で 10 秒から改定。処理は非同期なので利用者は待たない） |
| アップロード | 受け付けは即時応答。処理は非同期 |
| 最大ファイルサイズ | 1GB |

### 8.2 リソース配分（RAM 8GB の場合の目安）

| プロセス | 目安 |
|---|---|
| api（クエリ埋め込み用にモデルを常駐） | 〜1.5GB（上限） |
| worker（OCR + 埋め込み） | 〜3GB（上限） |
| Caddy / Samba / OS | 〜1GB |
| ページキャッシュ（SQLite・ベクトル） | 残り |

- worker の並列数は 1。CPU 温度が 80℃ を超えたら処理を一時停止する。

### 8.3 セキュリティ

外部公開はせず VPN 経由で使う前提。ログイン必須、argon2id、CSRF 対策、ログイン試行制限、アップロードファイルをブラウザで HTML として表示させない配信、監査ログ。詳細は [認証・権限・共有](design/security.md)。

### 8.4 運用

restic による日次バックアップ（原本 + DB スナップショット。ホストの systemd タイマー）、復旧の練習用スクリプト、管理画面での状態監視と警告（worker・ジョブ・ディスク・バックアップ・温度）、起動時の自動マイグレーション。詳細は [配置・運用](design/deployment.md)。

## 9. テスト方針

| 種類 | 対象 | 方法 |
|---|---|---|
| 単体テスト | チャンク分割、正規化、読み順の組み立て、RRF、クエリの解釈、権限の計算 | pytest。OCR・埋め込みはスタブに差し替える |
| 結合テスト | API（アップロード → 処理 → 検索 → 共有 → 削除） | pytest + httpx。一時ディレクトリに DB とファイルを作る。小さな実モデルで通しで動かすテストは別マークにする |
| セキュリティ | 権限の無いフォルダ・文書へのアクセス、共有リンクの期限・無効化、CSRF、危険なファイル形式の配信ヘッダ | 結合テストに含める |
| OCR 精度 | 代表的な文書 10〜20 ページ（横書き・縦書き・表・写真） | `scripts/eval_ocr.py` で文字誤り率（CER）を算出 |
| 検索品質 | 自分の文書に対する質問 30 件以上 | `scripts/eval_search.py` で Recall@5 / MRR（[検索設計](design/search.md) 9 章） |
| 性能 | 取り込み速度、検索の応答時間、温度 | Pi 5 実機で `scripts/bench_*.py` |

- CI（GitHub Actions）: lint（ruff）、型チェック（mypy）、単体・結合テスト。arm64 での動作確認は Pi 実機で行う。
- 評価用の実データはリポジトリに入れない。

## 12. 未決事項・リスク

| 項目 | 内容 | 対応 |
|---|---|---|
| OCR モデルのサイズ | PP-OCRv6 small で精度が足りるか（medium は予備計測で small の約 20 倍遅く、常用は難しい） | Phase 0 で実文書を比較。small を既定とし、文書ごとに medium で再処理できるようにする |
| 段組み・表の読み順 | 2 段組みや表で左右の段の文が混ざる（実文書で確認） | XY-cut によるブロック分割を追加（pipeline.md 4.4）。Phase 2 で効果を確認 |
| 簡体字の混入（優先度: 低） | 小さい文字で日本語の字形に簡体字が混ざることがある（例: 問題→問题、経済→经済）。目視確認では頻度は低く、実用上ほぼ無視できる | 対応しない。検索で困る事例が出たら、日本語の字形へ置き換える対応表（設定で無効化可）を追加する |
| 縦書き・表の精度 | PP-OCRv6 small で不足する可能性 | `OcrEngine` で抽象化し、medium モデルや YomiToku に差し替え可能にする |
| sqlite-vec の規模上限 | 10 万件で p95 80ms（実測）。100 万件では 800ms 前後の見込みで目標を超える。int8 は容量 1/4 だが検索は遅くなる | 10 万件までは対策不要。超えたら bit 量子化 + 並べ直し、または Qdrant へ移行 |
| 2 文字以下の語の検索 | trigram で検索できない | 意味検索の候補内で照合（制約あり）。必要なら 2-gram 索引を追加 |
| HEIC 対応 | arm64 でのデコード | pillow-heif（Linux aarch64 の wheel あり）で対応する（[拡張機能](design/extensions.md) 4 章） |
| LLM のメモリ | RAM 8GB では api・worker・llm でほぼ使い切る | LLM は既定で無効。有効にするなら 16GB を推奨。8GB では 1B 以下のモデル（Phase 9 で計測） |
| 外部との通信 | URL の取り込みで LAN の機器を突かれる（SSRF） | 取得は fetcher に分け、接続先の IP の確認・固定、リダイレクトごとの再確認（[拡張機能](design/extensions.md) 6.3） |
| イメージのビルド場所 | 当面は Pi 上で `docker compose build`（Python のみで依存も少ないため数分）。OCR・埋め込みの依存が入る Phase 2 で、ビルド時間を見て CI の arm64 ランナーへの移行を判断 | Phase 2 で再検討 |
| 熱・SSD 寿命 | 長時間の OCR バッチ、SQLite の書き込み | アクティブクーラー必須、温度での一時停止、SMART の定期確認 |
